IMPLEMENTATION STATUS — 2026-10-02
This document is a design reference, not evidence that every feature is complete.
The current implementation and verification limitations are documented in
docs/PROJECTFORGE_ARCHITECTURE.md and docs/IMPLEMENTATION_STATUS.md.
Specialists execute real model calls when GEMINI_API_KEY is configured.
Offline understanding uses explicitly labelled rules; it is not local AI inference.
The coding adapter uses the configured Gemini model, not Qwen.
Generated-code execution requires the provided Docker runtime; no host fallback exists.
VERIFIED requires backend, acceptance, frontend and declared browser checks as applicable.
Missing runtime, failures or exhausted repairs cannot transition to SHIP.
API/browser acceptance cases are frozen before coding. Their coverage is not proof of
security, load capacity, accessibility or universal correctness.

PART 1: COMPREHENSIVE WORK PROCESS FOR EACH AI AGENT
################################################################################

--------------------------------------------------------------------------------
1. INTAKE & PROJECT UNDERSTANDING AGENT (IntakeHost / Elena)
--------------------------------------------------------------------------------
• Primary Purpose:
  Deconstructs an ambiguous, unstructured natural language prompt into a structured,
  auditable architectural representation across 17 foundational dimensions.

• Input Data:
  - Raw natural language prompt (e.g. "I want to build a student assignment evaluation platform").
  - Execution mode ("AUTONOMOUS" or "GUIDED").

• Internal Work Process:
  1. Semantic Tokenization & Scope Analysis: Extracts keywords, domain concepts, and intended scale.
  2. 17-Dimensional Decomposition: Evaluates prompt across:
     (1) Problem Statement, (2) Core Goals, (3) User Personas, (4) Functional Scope,
     (5) Non-Goals, (6) Data Models, (7) Integrations, (8) SLA/Performance,
     (9) Scalability, (10) Security/Auth, (11) UX States, (12) Tech Stack,
     (13) Risks, (14) Assumptions, (15) Unknowns, (16) Cost, (17) Acceptance Criteria.
  3. Provenance Tagging: Distinguishes explicit user demands from inferred assumptions:
     - source = "USER" (Explicitly requested by user)
     - source = "INFERENCE" (Derived by architectural common sense)
     - source = "AGENT" (Recommended by engineering best practice)

• Output Artifacts:
  - ProjectContext (Version 1)
  - ExtractedRequirementItem collection
  - Ambiguity & Unknowns list (UNK-001...UNK-NNN)


--------------------------------------------------------------------------------
2. REQUIREMENT ENGINE & MATERIALITY FILTER
--------------------------------------------------------------------------------
• Primary Purpose:
  Prevents question fatigue. Decides whether an unknown requires human clarification
  or can be safely assigned a production-grade sensible default.

• Input Data:
  - Extracted Unknowns and Requirements from Intake Agent.

• Internal Work Process:
  1. Materiality Evaluation: For each unknown, computes an Impact Score:
     - High Impact (Architectural Blocker): Core datastore paradigm, auth model, billing gateway.
     - Low Impact (Sensible Default): Theme color, font, default pagination size.
  2. Question Generation: If high-impact unknown exists, formulates exactly ONE targeted,
     multiple-choice question with clear trade-offs and consequences.
  3. Decision Recording: When user answers, records the choice into an immutable Decision Log
     with timestamp, confidence (1.0), and increments Context version (v1 -> v2).

• Output Artifacts:
  - ClarificationQuestion (or null if all unknowns safely defaulted)
  - DecisionRecord
  - Validated ProjectContext

3. PRODUCT MANAGER AGENT (Elena Rostova)
--------------------------------------------------------------------------------
• Role Accent: #10B981 (Emerald)
• Primary Purpose:
  Defines market scope, target user personas, and prioritized functional requirements.

• Input Data:
  - Validated ProjectContext, Decision Log, Scope constraints.

• Internal Work Process:
  1. Persona Construction: Identifies primary and secondary user roles with goals and pain points.
  2. Scope Boundary Capping: Defines strict MVP scope (Phase 1) vs Future Roadmap (Phase 2+).
  3. Functional Specification: Creates atomic, numbered functional requirements (FR-001...FR-NNN).

• Output Artifacts:
  - Product Specification (`prd.md`)
  - User Persona Matrix, OKR Metrics table, MVP Feature Checklist.

4. AI/ML ARCHITECT AGENT (Dr. Aris Thorne)
--------------------------------------------------------------------------------
• Role Accent: #A855F7 (Purple)
• Primary Purpose:
  Evaluates whether Machine Learning or generative AI is strictly necessary or if a 
  deterministic heuristic/rule-based algorithm is superior.

• Input Data:
  - Functional requirements, SLA targets, operational cost limits.

• Internal Work Process:
  1. Zero-AI vs ML Assessment: Evaluates cost, maintenance, and latency overhead.
  2. Architecture Selection: If ML needed, determines model type (NLP, CV, Vector Embeddings, LLM).
  3. Latency & Budget Validation: Specifies inference SLA (e.g. <50ms) and hardware constraints (CPU vs GPU).

• Output Artifacts:
  - AI/ML Architecture Spec (`model_decision.md`)
  - Necessity justification, model parameters, fallback heuristic.

5. ENGINEERING LEAD AGENT (Marcus Vance)
--------------------------------------------------------------------------------
• Role Accent: #3B82F6 (Blue)
• Primary Purpose:
  Designs high-performance system topology, database schemas, and microservice APIs.

• Input Data:
  - PRD, AI Spec, SLA targets, scale projections.

• Internal Work Process:
  1. Architectural Topology: Selects pattern (Modular Monolith, Microservices, Event-Driven).
  2. Schema Design: Defines relational/document tables, primary keys, indexing, and foreign keys.
  3. API Protocol Specification: Defines RESTful endpoints, SSE streaming routes, or gRPC methods.
  4. Mermaid Visualization: Generates live syntax-valid system topology diagrams.

• Output Artifacts:
  - Engineering Specification (`arch_diagram.md`)
  - Mermaid topology diagram, Entity-Relationship schema, API endpoint dictionary.


--------------------------------------------------------------------------------
6. UX DESIGNER AGENT (Sora Takahashi)
--------------------------------------------------------------------------------
• Role Accent: #EC4899 (Pink)
• Primary Purpose:
  Maps the complete user journey and defines mandatory UI view states for every screen.

• Input Data:
  - User personas, user stories, product features.

• Internal Work Process:
  1. Journey Flow Mapping: Maps step-by-step clicks from entry to task completion.
  2. Four-State View Contract: Enforces 4 mandatory states for every screen:
     - Loading State (Skeletons/Spinners)
     - Empty State (Zero-data onboarding CTA)
     - Error State (Graceful recovery & retry banner)
     - Success State (Active populated interface)
  3. Design Tokens: Specifies responsive breakpoints, color palette, and component hierarchy.

• Output Artifacts:
  - UX Specification (`ux_spec.md`)
  - Screen state transition matrix, wireframe specifications.


--------------------------------------------------------------------------------
7. SECURITY AUDITOR AGENT (Kaelen Cross)
--------------------------------------------------------------------------------
• Role Accent: #EF4444 (Red)
• Primary Purpose:
  Performs threat modeling, access control audits, and vulnerability mitigation.

• Input Data:
  - System topology, API specs, database entities, authentication requirements.

• Internal Work Process:
  1. STRIDE Threat Analysis: Evaluates Spoofing, Tampering, Repudiation, Information Disclosure,
     Denial of Service, and Elevation of Privilege.
  2. Authentication & Authorization Design: Formulates OAuth2/JWT token signing, session TTL,
     and Role-Based Access Control (RBAC) permission matrices.
  3. Encryption Standards: Enforces TLS 1.3 in transit and AES-256 at rest.

• Output Artifacts:
  - Security Audit Report (`threat_model.md`)
  - STRIDE mitigation catalog, RBAC matrix, token lifecycle specification.


--------------------------------------------------------------------------------
8. QA STRATEGIST AGENT (Devon Reed)
--------------------------------------------------------------------------------
• Role Accent: #F59E0B (Amber)
• Primary Purpose:
  Designs the automated test pyramid, regression strategy, and verification budgets.

• Input Data:
  - Functional requirements (FR), Non-functional requirements (NFR), APIs.

• Internal Work Process:
  1. Test Pyramid Distribution: Allocates 70% Unit, 20% Integration, 10% End-to-End.
  2. Traceability Linking: Maps every test case directly back to a traceable Requirement ID (TEST-001 -> FR-001).
  3. SLA Validation: Formulates automated latency benchmarks and error handling assertions.

• Output Artifacts:
  - Verification & Test Strategy (`test_strategy.md`)
  - Critical test case specifications, assertion contracts, coverage targets (>=85%).


--------------------------------------------------------------------------------
9. CONFLICT RESOLVER / ARBITER AGENT (Lex)
--------------------------------------------------------------------------------
• Role Accent: #06B6D4 (Cyan)
• Primary Purpose:
  Detects and arbitrates architectural contradictions between specialist proposals.

• Input Data:
  - Aggregated agent specifications (e.g. AI wants WebSockets vs Engineering wants REST).

• Internal Work Process:
  1. Contradiction Detection: Identifies competing recommendations across protocols, databases, or constraints.
  2. Multi-Criteria Weighted Trade-Off Scoring: Evaluates competing options on 5 dimensions:
     - Maintainability (weight: 0.25)
     - Performance / Latency (weight: 0.25)
     - Implementation Complexity (weight: 0.20)
     - Infrastructure Cost (weight: 0.15)
     - Scalability (weight: 0.15)
  3. Formal ADR Authoring: Synthesizes the decision into an Architectural Decision Record (ADR)
     with selected solution, rejected alternatives, and justification.

• Output Artifacts:
  - Architectural Decision Records (`adr_records.md`)
  - Multi-criteria score matrix, arbitration audit trail.


--------------------------------------------------------------------------------
10. FINAL ARCHITECT AGENT (Prime)
--------------------------------------------------------------------------------
• Role Accent: #6366F1 (Indigo)
• Primary Purpose:
  Synthesizes all specialist outputs, ADRs, and requirements into the 27-section Master Blueprint.

• Input Data:
  - All 6 specialist specs, resolved conflict ADRs, ProjectContext.

• Internal Work Process:
  1. Full Traceability Synthesis: Builds bidirectional audit matrix mapping:
     User Prompt -> Requirement ID -> Specialist Spec -> ADR -> Blueprint Section.
  2. Document Compilation: Generates all 27 canonical blueprint sections (Executive Summary,
     Scope, Topology, API Contracts, Database Schema, STRIDE, QA, Tech Stack Table, Acceptance Criteria).

• Output Artifacts:
  - Master Architectural Blueprint (`FINAL_PROJECT_BLUEPRINT.md`)
  - Bidirectional requirement audit traceability matrix.


--------------------------------------------------------------------------------
11. BUILD SPEC COMPILER
--------------------------------------------------------------------------------
• Primary Purpose:
  Translates the human-readable Master Blueprint into a machine-readable, strictly 
  typed JSON specification for physical code generation.

• Input Data:
  - ProjectContext, Blueprint, Architectural Specs.

• Internal Work Process:
  1. Pydantic Schema Compilation: Generates `.projectforge/build_spec.json`.
  2. Requirement Provenance Tagging: Enforces explicit `source = "USER" | "AGENT" | "INFERRED"`.
  3. Anti-Hallucination Gate: If critical datastore or auth architecture is missing,
     emits structured `BLOCKED` status instead of inventing assumptions.

• Output Artifacts:
  - `.projectforge/build_spec.json` (Machine-Readable Build Specification)


--------------------------------------------------------------------------------
12. TASK GRAPH & SCHEDULER
--------------------------------------------------------------------------------
• Primary Purpose:
  Decomposes the Build Spec into an acyclic directed graph (DAG) of atomic coding tasks.

• Input Data:
  - `.projectforge/build_spec.json`.

• Internal Work Process:
  1. Atomic Task Generation: Creates tasks (TASK-001 Scaffold, TASK-002 Models, TASK-003 API, 
     TASK-004 Tests, TASK-005 Frontend Manifest, TASK-006 UI Components).
  2. Topological Sort: Applies Kahn's algorithm to determine non-cyclic execution order.
  3. Dynamic Unlocking: As tasks transition to `COMPLETED`, automatically unlocks downstream 
     tasks from `PENDING` to `READY`.

• Output Artifacts:
  - `.projectforge/task_graph.json`
  - Ordered task queue with strict file modification boundaries.


--------------------------------------------------------------------------------
13. REPOSITORY & GIT MANAGER
--------------------------------------------------------------------------------
• Primary Purpose:
  Guarantees isolated file surgery, prevents path traversal, and maintains version checkpoints.

• Input Data:
  - File write requests from Coding Agent, Task IDs.

• Internal Work Process:
  1. Path Traversal Defense: Verifies all paths remain strictly inside `generated_projects/{id}/`.
  2. Scope Enforcement: Rejects edits if a task attempts to touch unauthorized files.
  3. Git Checkpointing: Creates commits at major milestones: `initial_scaffold`, `code_complete`,
     `repair_successful`, `verified`. Supports rollback upon repair failure.

• Output Artifacts:
  - Real files written on disk.
  - `.projectforge/checkpoints.json`


--------------------------------------------------------------------------------
14. CODING ORCHESTRATOR & CODING AGENT (Qwen3-Coder)
--------------------------------------------------------------------------------
• Role Accent: #22C55E (Green)
• Primary Purpose:
  Synthesizes production-grade source code for each atomic task using controlled tools.

• Input Data:
  - READY tasks from Task Scheduler, pruned task-specific context.

• Internal Work Process:
  1. Context Pruning: Receives only relevant schemas, requirements, and constraints for that task.
  2. Controlled Tool Execution: Modifies code exclusively through `read_file`, `write_file`,
     `modify_file`, and `search_code`.
  3. Code Synthesis: Produces clean FastAPI endpoints, Pydantic models, and React UI components.

• Output Artifacts:
  - Source code files (`backend/app/main.py`, `models.py`, `App.tsx`, etc.)
  - Structured TaskImplementationResult report.


--------------------------------------------------------------------------------
15. SAFE COMMAND EXECUTOR & TEST RUNNER
--------------------------------------------------------------------------------
• Primary Purpose:
  Safely executes development commands and automated test suites in a subprocess sandbox.

• Input Data:
  - Commands requested (`pytest`, `npm test`, `git`).

• Internal Work Process:
  1. Whitelist Verification: Evaluates command against approved binaries (`python`, `pytest`, `pip`, `npm`, `git`).
     Blocks dangerous commands (`rm -rf`, `del /f`, `powershell -c`).
  2. Sandboxed Subprocess: Runs command in project root with execution timeout (60s).
  3. Output Parsing: Parses stdout/stderr, exit codes, and assertion failures into structured JSON.

• Output Artifacts:
  - `.projectforge/test_results.json`
  - ExecutionResult (exit code, duration ms, stdout, stderr).


--------------------------------------------------------------------------------
16. DEBUGGER AGENT, FAILURE CLASSIFIER & SELF-HEALING LOOP
--------------------------------------------------------------------------------
• Primary Purpose:
  Automatically diagnoses test failures and applies targeted repair patches (capped at 3 attempts).

• Input Data:
  - Failed `TestRunResult` from Test Runner.

• Internal Work Process:
  1. 12-Category Classification: Classifies error into: SYNTAX_ERROR, DEPENDENCY_ERROR, 
     TYPE_ERROR, DATABASE_ERROR, API_ERROR, TEST_FAILURE, FRONTEND_ERROR, etc.
  2. Root Cause Hypothesis: Pinpoints exact file, line number, and mismatch reason.
  3. Pre-Repair Checkpoint: Git commits `checkpoint: pre_repair_attempt_N`.
  4. Patch & Retest: Applies surgical code replacement and re-runs pytest.
  5. Bounded Escalation: If not passing after 3 attempts, halts and marks `REQUIRES_HUMAN`.

• Output Artifacts:
  - `.projectforge/repair_history.json`
  - Healed verified project or human review escalation report.


--------------------------------------------------------------------------------
17. VS CODE LAUNCHER
--------------------------------------------------------------------------------
• Primary Purpose:
  Launches the generated project in Visual Studio Code only after verification succeeds.

• Input Data:
  - Generated project path, `.projectforge/test_results.json`.

• Internal Work Process:
  1. Pre-Flight Verification: Asserts workspace exists, files exist, and test suite exited with code 0.
  2. CLI Detection: Locates `code` or `code.cmd` binary on system PATH.
  3. Process Launch: Executes `code <workspace_path>`.

• Output Artifacts:
  - Running Visual Studio Code window with generated project open.
